# 합주 피드백 앱 — 기술 PoC 요약

**앱 컨셉**: 합주 피드백이 카톡·메모로 흩어지는 밴드 멤버에게, 악보·녹음 위 구간별 피드백을 모아 개인 연습 과제로 이어주는 iPad 앱.

---

## 1. 세션별 음원 분리

### 어떤 모델들이 있나

| 모델 | 특징 |
|---|---|
| Spleeter (Deezer) | 가장 오래됨, 가볍고 빠르지만 품질은 요즘 기준으로 낮음 |
| Open-Unmix | 학계 기준 모델(baseline), 4-stem |
| **Demucs 계열 (Meta/FAIR)** | v1~v4 발전, 현재 오픈소스 중 사실상 SOTA |
| MDX-Net | Music Demixing Challenge 2021 우승, 보컬 분리 특히 강함 |
| Moises.ai / LALAL.AI / Audioshake | 상용 클라우드 API, 기타·피아노 등 비주류 악기도 품질 좋은 편이나 유료 + 오디오를 외부 서버로 보내야 함 |

### 우리가 쓴 것

**Demucs `htdemucs_6s`** (Hybrid Transformer, Meta 오픈소스) — 무료·오프라인 실행 가능해서 "로컬 서버" 구조와 맞음. 6-stem 버전이라 보컬/드럼/베이스/**기타/피아노**/기타(other)까지 한 번에 나옴.

### 서버 구조

- **로컬 Python(FastAPI) 서버**가 분리 연산 전담, iPad 앱은 업로드 → 폴링 → 스템 다운로드만 담당
- Apple Silicon MPS(GPU) 가속, 4분 곡 기준 20~40초

### 결과

- ✅ **보컬/드럼/베이스는 안정적** — 4-stem 조합은 실사용 가능한 수준
- 🔴 **일렉기타·피아노는 품질이 떨어짐** — 두 가지 원인이 겹쳐 있는 것으로 보임:
  1. **모델 자체의 한계**: Demucs가 기타/피아노 카테고리를 더 적은/약한 데이터로 학습해서 보컬/드럼/베이스보다 원래 약함
  2. **녹음 환경 영향**: 합주실 통합 녹음(방 하나 마이크)은 스튜디오 멀티트랙과 달라서, 악기 간 소리가 섞이고 잔향이 커서 원래도 약한 카테고리(기타/피아노)가 더 취약해짐

→ **다음 결정**: 기타/피아노 품질이 꼭 필요하면 상용 API(Moises 등)를 별도 검토하거나, 녹음 가이드(마이크 위치 등)를 제품에서 안내하는 것도 방법. 아니면 4-stem으로 스코프를 좁히는 것도 현실적 선택.

## 2. 악보 ↔ 녹음 싱크

### 핵심 발견: 상황에 따라 "싱크가 되는 녹음"과 "안 되는 녹음"이 다르다

| 상황 | 메트로놈 사용 | 싱크 가능 여부 |
|---|---|---|
| **합주(밴드 전체 연습)** | ❌ 안 씀 | 템포가 자유롭게 흔들림 → 템포 계산만으론 안 맞음 (실제로 19% 오차 확인됨) |
| **개인 연습** | ✅ 메트로놈 들으며 연습 | 정박에 고정됨 → 템포 계산이 그대로 맞을 가능성 높음 |
| **유튜브 원곡 재생하며 연습** | 원곡 자체가 원래 박자 | 원곡 템포 = 악보 표기 템포와 일치 → 템포 계산이 그대로 맞음 |

즉 "왜 안 맞았는지"가 이제 명확해졌습니다 — **합주 녹음에는 애초에 고정된 박자 기준(클릭)이 없기 때문**입니다. 반대로 개인 연습·유튜브 재생은 애초에 고정 박자를 따라가므로 계산만으로 충분할 가능성이 큽니다.

### MuseScore식 vs Chordify식 — 어느 쪽으로 갈까

두 방식을 오디오 소스별로 **다르게** 적용하는 게 맞습니다:

- **MuseScore식** (악보 템포를 그대로 신뢰해서 계산): 오디오가 애초에 고정 박자를 따라갈 때만 성립 (신스가 곡을 만들 때처럼, "정답 템포"가 실제로 지켜지는 경우)
  → **개인 연습(메트로놈) / 유튜브 원곡 재생**에 적용 — 지금 만든 템포 계산 로직 그대로 사용 가능, 보정 불필요할 가능성 높음

- **Chordify식** (실제 오디오를 분석해서 타이밍을 역산): 오디오 자체에 고정 기준이 없을 때 필요
  → **합주 녹음**에 적용 — 예를 들어 이미 분리된 **드럼 스템으로 비트 트래킹**을 하거나, 악보에 적힌 코드 진행(Bm→D/F#→G...)과 실제 녹음에서 검출한 코드 변화 시점을 매칭하는 방식

**정리**: "녹음 소스가 뭐냐"에 따라 자동으로 전략을 나누는 게 정답입니다.
- 개인 연습 녹음, 유튜브 재생 → 템포 계산 (지금 있는 기능 그대로, 보정 거의 불필요)
- 밴드 합주 녹음 → 비트 트래킹/코드 매칭 필요 (추가 검증 대상) 또는 지금 만든 수동 보정 모드로 우회

## 3. YouTube 연동 — ✅ 검증 완료

**결정 & 결과**: 직접 만든 WKWebView 코드 대신 **[YouTubePlayerKit](https://github.com/SvenTiigi/YouTubePlayerKit)** 라이브러리로 교체 → **시뮬레이터에서 실제 재생 성공**

- 이전엔 손으로 짠 WKWebView 브릿지가 JS 통신까지는 됐지만 실제 재생이 막혔음(서드파티 쿠키 차단 등 잘 알려진 WKWebView 이슈, 오류 152/153)
- YouTubePlayerKit으로 교체하자마자 같은 시뮬레이터에서 영상 썸네일·재생·재생시간이 전부 정상 동작 — 실기기 테스트 없이도 이 단계는 확정
- Swift 네이티브 `currentTimePublisher`로 재생 위치를 실시간 구독해서 `ScoreSyncController`에 그대로 연결 → **재생 위치에 맞춰 악보 자동 넘김까지 실제로 동작 확인** (1페이지 → 2페이지 전환을 재생 중 실시간으로 확인)

### 보정 모드 로직 개선

같은 곡의 실제 방송 클립(3:45)이 악보 표기 템포(185BPM, 이론상 188초)보다 느리게 편곡돼서, 템포 계산이 실제 음악보다 **앞서서** 페이지를 넘기는 문제를 발견. 보정 버튼이 "자동계산이 이미 틀려서 앞서나간 페이지"를 기준으로 다음 페이지를 정하는 구조라 보정 자체가 엉뚱한 페이지에 기록될 수 있는 버그였음 → **보정 모드 중엔 화면이 자동계산을 따라가지 않고, 사용자가 누른 만큼만 페이지가 넘어가는 별도 커서로 분리**해서 해결.

## 4. 악보 위 손글씨 메모 + 공유

**결정**: **Apple PencilKit + CloudKit**

- PencilKit: 손글씨 작성/저장 — PoC에서 이미 검증 완료 (페이지 고정 크기 렌더링 + 캔버스 좌표 일치, 앱 재시작해도 위치 복원됨)
- CloudKit: 멤버 간 공유 — Sign in with Apple + CKShare로 서버 직접 운영 없이 구현
- 단, "피드백 하나하나를 특정 멤버 조합에게만" 공유하는 건 CloudKit의 기본 공유 모델과 결이 달라서, 밴드 전체를 하나의 공유 영역으로 묶고 **누구에게 보일지는 앱이 필드값으로 필터링**하는 절충안으로 진행

## 5. 구간 반복 재생 — ✅ 검증 완료

**질문**: 어려운 마디를 계속 돌려 들으며 연습할 수 있는 A-B 구간 반복 기능이 가능한가?

- "구간 시작"/"구간 끝" 버튼으로 현재 재생 위치를 캡처해서 구간 지정, "구간 반복" 켜면 그 구간을 끊김 없이 순환 재생
- 재생 위치가 구간을 벗어난 상태에서 반복을 켜도, 즉시 구간 안으로 점프해서 반복 시작

**검증 결과**: 구간(0:01~0:05) 밖(0:41)에서 반복을 켜고 재생 → 즉시 구간 안으로 점프 → 구간 끝에서 시작으로 자동 복귀하며 순환 재생되는 것을 실시간으로 확인. 반복 중에도 악보 자동 넘김은 정상 동작(구간이 1페이지 범위 안이라 1페이지 유지).

> **디버깅 메모**: 시뮬레이터 자동 탭 테스트가 "재생 중(화면이 0.1초마다 갱신)"일 때는 잘 씹히고 "일시정지 상태"에서는 안정적으로 먹히는 패턴을 발견 — 다음에 이 시뮬레이터로 UI 자동 테스트할 때 참고.
